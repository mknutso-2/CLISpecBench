# RS274 migration to v3.2.2 grading — runbook

Working instructions for regrading the published RS274 record onto the v3.2.2 rubric. Read
[`Regrading.md`](Regrading.md) first, especially "Cohort rules for any official migration"; this
document is the concrete plan, those rules are the constraints.

**Nothing here authorizes changing `published_results/`.** A regrade produces a separate
observation. Migrating the dashboard is a later, explicit decision by the repository owner.

## Why a migration is legitimate here

The v3.2.2 changes were test/scoring-only. Model-visible inputs did not change, which is the
condition that makes regrading old source comparable rather than a generation/grading mismatch.
Verified across the published record:

| Task | prompt_content_sha at 3.1.11 | at 3.2.0 |
|---|---|---|
| rs274-cpp | `c95aba8dfeb1` | `c95aba8dfeb1` |
| rs274-py | `8d46bad32c13` | `8d46bad32c13` |
| rs274-js | `a768fd2f621d` | `a768fd2f621d` |
| rs274-rs | `1290cae73782` **and** `35713dbfd826` | `1290cae73782` |

Every language but Rust is single-hash across both eval versions. See "Rust prompt variant" below.

### The two unregradeable rows

`rs274-js` gpt-5.4-mini xhigh (`79266582-254d-4b07-9834-af8d1bf7ad3c`) and `rs274-py`
gemini-3-flash-preview (`fe7bf6d1-bc3e-46c3-886a-86c4db28efd1`). Both have a transient run
directory but no `source/`.

**Decision: keep both at their original rubric, explicitly labelled.** Do not silently leave them
beside migrated rows, and do not retire them.

This is not harness data loss. Both are agent-side output-contract failures: the agent finished
without creating `/workspace/output`, so there was no source to preserve. The harness recorded the
condition three independent ways — `source_stats.file_count: 0`, `build.success: false`, and 546
errored cases — rather than scoring an empty submission as anything else. The gemini row carries a
contemporaneous root-cause note in its `metadata.notes`. The same pattern accounts for nearly all
206 sourceless transient RS274 runs, whose `exit_reason` is overwhelmingly `error` or `no_output`;
only these two were ever published.

Their scores are also **rubric-invariant**: a submission containing no code scores zero under any
suite. Compare `rs274-rs` gpt-5.6-terra low, which did preserve source but never built, and
regraded 0/546 → 0/555. Leaving these two rows unmigrated therefore costs no information and
introduces no bias.

```bash
python - <<'EOF'
import json
from pathlib import Path
for p in Path('published_results/rs274-rs').glob('*/*/run*.json'):
    m = json.loads(p.read_text())['metadata']
    if not str(m.get('prompt_content_sha')).startswith('1290cae7'):
        print(m['run_uid'], m.get('model'), m.get('effort'))
EOF
```

These are regradable — the tests are what changed — but they carry a genuine model-input
difference on top of the grading change.

**Decision: regrade them, but keep them as a separately labelled sub-cohort.** Do not pool them
with same-prompt Rust rows in a single ranking, and state the prompt difference wherever they
appear alongside `1290cae73782` rows.

## The grader image, and how to avoid moving one

The committed Astra regrades used image
`sha256:9a4f1fe0219b50b94c4a7abeb8a48cedd6a9c17c1ab90d34cc4bb4d826a7c90c`. The primary workstation
has `sha256:922c3bc7435e5546e737bf77b5bc8c07d15f86c9bad7f6fc68555cf8fbf04dc5`. Pinned image IDs
are not reproducible from `docker/base.Dockerfile`, so the images cannot simply be rebuilt to
match.

Transferring an image is possible (`docker save` to a tarball, `docker load` on the other host)
but it is a multi-gigabyte manual file copy and has nothing to do with git — image tarballs must
never be committed.

**Preferred alternative: demonstrate equivalence instead of enforcing identity.** Whoever holds an
image runs the four reference implementations under it and compares against the figures in
`docs/validation/RS274-3.2.2.md`. If both images reproduce the same reference results, cross-image
comparability is measured rather than assumed, and no file transfer is needed.

Expected under the v3.2.2 suite (test hash
`3d096665fab1578444b0c0a0f7bfa1975e389a9398a34e265820305b300eca11`):

| Reference | Expected |
|---|---:|
| Python | 555/555 |
| Rust | 555/555 |
| C++ | 447/555 |
| JavaScript | 447/555 |

Already measured under `922c3bc7`: C++ 447/555, Python 555/555, JavaScript 447/555 — all matching.
Rust could not be built there because the reference needs `serde` and `serde_json` and an offline
build has no populated cargo cache; a host with a warm cargo registry can close that gap.

**The outstanding task for the machine holding `9a4f1fe0`** is to run this control and record the
four figures. That is minutes of work and it retires the mixed-image caveat. Regrading the Astra
submissions again is *not* required — their 3.2.2 records already exist.

## Running a regrade

```bash
uv run clispecbench regrade <transient>/result.json --output-dir <new-empty-dir>
```

- Input must be the **transient** run directory with its preserved `source/`. A published
  `run1.json` alone is not sufficient.
- Docker is the default and is what counts; `--local` is a host diagnostic only.
- Select the run by **published run UID**, never by score or directory order. A
  `<model>_<effort>` label can cover several saved runs of which only one was published.
- The output directory must be new or empty and outside the original run directory.
- On Windows, a saved Rust `target/debug/incremental/` tree can exceed MAX_PATH when copied into a
  long output path. Symptom is a `copytree` error naming `work-products.bin`. Use a short output
  directory such as `%TEMP%\rg1`.
- A grader failure exits non-zero and writes `grading.status = "failed"` with null scores. Never
  convert that into a zero — investigate it.

## Emitting a portable cohort

Raw bundles include full source snapshots and are not committed. Follow the shape of the two
existing cohorts: one `clispecbench.regrade-summary` JSON per submission, a `manifests/`
directory, `scores.csv`, and a README stating selection rule, grader image, test hash and limits.

There is no summary emitter in the harness; both existing cohorts were produced by ad-hoc scripts.
If you write another, note these traps, both of which produced real defects:

- Compute the prompt digest with `hash_prompt_content(task)` — passing `"base"` as the variant
  relabels the manifest entry and silently yields a different digest.
- Preserve **actual** outcome strings in transition counts. Collapsing every non-pass to `failed`
  misreports build and collection errors; a submission that never built shows `error -> error`,
  not `failed -> failed`.

Keep full per-test failure messages. They look expensive on disk (~15 MB for 36 records) but git
packs them to about 5% of that, and they are what makes a regression diagnosable.

## Verification before publishing any cohort

At minimum, check that: the cohort UID set equals the intended published UID set; every record has
`grading.status == "completed"` with the expected total, no skips and no infrastructure errors; one
test hash and one image across the cohort; `len(tests) == test_summary.total` with unique node IDs;
per-outcome counts reconcile against both the summary and the CSV; `published_result_sha256` and
`archived_result_sha256` recompute against the live files; and every referenced manifest exists.

`automation_logs/rs274-audit-codex/review36.py` is an existing independent checker for the GPT-5.6
cohort and is a reasonable template.
