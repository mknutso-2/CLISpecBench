I work in scheduling automation and I need a tool that reads the iCalendar `.ics` files our partners and internal systems produce and answers two kinds of questions: (1) what's in the file — a fully decoded structure with every VEVENT / VTODO / VJOURNAL / VFREEBUSY / VTIMEZONE / VALARM and their properties, recurrence rules, attendees (full ATTENDEE grammar with ROLE, PARTSTAT, DELEGATED-FROM/TO, CUTYPE, MEMBER, DIR, CN), timezone definitions, and calendar-level properties (METHOD, NAME, REFRESH-INTERVAL, COLOR, IMAGE, CONFERENCE); (2) for a date window I specify, what are the actual concrete event instances — all the recurring events expanded per their RRULE, RDATE (including VALUE=PERIOD), EXDATE, and `RECURRENCE-ID` overrides (including `RANGE=THISANDFUTURE`), with zoned date-times correctly resolved through any VTIMEZONE definitions the file includes. The tricky parts are the full RRULE grammar (every BYxxx part, BYSETPOS, WKST, COUNT/UNTIL, the fixed application order, invalid-date dropping, non-Gregorian RSCALE per RFC 7529) and VTIMEZONE resolution (STANDARD/DAYLIGHT observances with their own RRULEs, TZUNTIL-bounded historical reloads, applying TZOFFSETFROM/TZOFFSETTO to convert local to UTC, DST-boundary fold disambiguation) — I'm feeding it real calendar files that our partners send, not simplified test cases.

Please read the specifications in the `docs/` directory carefully. The `docs/authoritative/` folder contains the actual IETF RFCs that define this format — RFC 5545 (core iCalendar), RFC 5546 (iTIP scheduling), RFC 6868 (parameter value escaping), RFC 7529 (non-Gregorian RRULEs), and RFC 7986 (new calendar properties). **These RFCs are the authoritative specification.** The `docs/summary.md` is a reading index that helps orient an implementer — useful as a starting point, but the RFCs govern behavior when they disagree.
